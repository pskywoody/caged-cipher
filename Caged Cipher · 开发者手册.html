1.3 快速启动

1.3.1 启动本地开发服务

项目为纯静态前端，无需编译，启动任意 HTTP 静态服务即可：

# 方式一：Python 内置服务（推荐，无需安装）
cd cagemaster3
python -m http.server 8080

# 方式二：Node.js http-server
npx http-server -p 8080 cagemaster3

# 方式三：PHP 内置服务
cd cagemaster3
php -S localhost:8080

启动后在浏览器打开：http://localhost:8080/guide.html

💡 小技巧

直接用 file:// 协议打开 guide.html 也能运行，但部分浏览器会限制音频自动播放和 fetch 请求，建议使用 HTTP 服务。

1.3.2 手机测试方法

确保手机和电脑在同一个 Wi-Fi 网络下，按以下步骤操作：

  1. 启动本地服务（绑定 0.0.0.0 以允许局域网访问）：

    cd cagemaster3
python -m http.server 8080 --bind 0.0.0.0

  2. 查看电脑局域网 IP：

    # Windows PowerShell
(Get-NetIPAddress -AddressFamily IPv4 | Where-Object {
  $_.InterfaceAlias -notmatch 'Loopback|vEthernet'
}).IPAddress

# 或简化命令
ipconfig | findstr "IPv4"

    当前开发机 IP：192.168.2.20

  3. 手机浏览器访问：

    在手机浏览器地址栏输入：http://192.168.2.20:8080/guide.html

  4. 直达指定关卡：

    在 URL 后加 ?id=关卡编号，例如：
    http://192.168.2.20:8080/guide.html?id=204

⚠️ 注意事项
  • 电脑防火墙需允许 8080 端口入站
  • iOS Safari 可能需要手动允许音频播放（首次点击后解锁）
  • 修改 JS/CSS 文件后，手机端需强制刷新（清空缓存）才能看到更新
  • 建议使用 Chrome DevTools 的「Remote Devices」进行真机调试

1.3.3 缓存刷新与版本号

项目通过 URL 参数 ?v=N 控制静态资源缓存。修改 guide.html 中对应的 script 标签版本号即可强制浏览器加载新文件：

<script src="game/board.js?v=3"></script>
<script src="game/renderer.js?v=8"></script>
<script src="pages/guide.js?v=9"></script>

每次修改对应文件后，将版本号 +1 即可。

2.3.1 核心层（core/）

核心层提供整个应用的基础设施，是所有上层模块的基石。

GameContext.js

核心 中央状态

五层共享中央状态容器，聚合 player / level / decision / learning 四大状态域，是各层之间通信的唯一可信数据源。

DataStore.js

核心 数据持久化

统一数据存储层，封装 localStorage 操作，支持 9 大分类、全局版本管理、3 份备份轮转与校验和验证。

InputRouter.js

核心 输入路由

统一指针/键盘事件路由，支持触摸、鼠标、键盘三端输入，自动分发到对应处理器。

CellInputHandler.js

核心 输入处理

核心输入处理逻辑：填数、擦除、笔记切换，是棋盘交互的核心处理器。

EventBinder.js

核心 事件绑定

事件绑定器，统一管理 DOM 事件的绑定与解绑，支持批量注册与清理。

error-reporter.js

核心 错误上报

全局错误捕获与上报系统，window.onerror / unhandledrejection 双重兜底，错误日志持久化到本地。

PerformanceMonitor.js

核心 性能监控

FPS 实时检测 + 三级画质自动降级，根据设备性能动态调整渲染质量。

ModuleInitializer.js

核心 模块初始化

模块初始化器，按依赖顺序加载各模块，处理初始化失败的降级与重试。

GuideOrchestrator.js

核心 应用编排

应用总编排器，负责装配所有模块、管理生命周期、协调跨模块通信。

constants.js

核心 全局常量

全局常量定义：Z_INDEX 层级体系、VIBRATE_PRESETS 震动预设、颜色主题等。

WhatIfManager.js

核心 假设模式

What-If 假设模式管理器，快照栈状态机，支持最多 3 层分支快照与回退。

GameController.js

核心 流程控制

游戏流程控制器，管理关卡加载、胜利判定、暂停/继续等宏观游戏状态。

DebugTools.js

核心 调试工具

调试工具集，暴露 DEBUG 全局对象，支持跳关、强制触发事件、性能面板等。

AISpeedController.js

核心 AI调速

AI 速度倍率控制器，根据三幕阶段和难度动态调整 AI 出手速度。

3.1.3 笼和校验机制

填数后自动校验笼子和值约束，不依赖答案数组：

  • 上限检测：当前和 + 剩余格子最小可能和 > 目标和 → 标错
  • 下限检测：当前和 + 剩余格子最大可能和 < 目标和 → 标错
  • 最小/最大可能和：从 1~size 中排除已用数字，取最小/最大的 N 个之和
  • 单格笼：填入后立即比对，不相等直接标错
💡 性能优化 笼和校验只在填数/擦除时触发，不在每帧 render 时计算，避免性能损耗。

3.5.3 求解策略

采用「最低可用技巧」策略，模拟真实人类解题路径：

  1. 从最低级技巧开始遍历
  2. 找到可填的格子 → 填数，记录为 fill 步骤，break
  3. 没找到可填的 → 检查是否有候选被排除（elimination）
  4. 有排除 → 记录为 elimination 步骤，break
  5. 下一轮从最低级技巧重新开始

这种「排除一步就回头」的策略，确保求解路径与人类思考顺序高度一致。

3.5.4 难度评分算法

baseScore = maxTechLevel × 100        // 最高技巧等级基础分
score = baseScore
      + remainingFactor × 100        // 剩余空格修正
      + densityFactor × 50           // 非孤星比例修正

星级划分：1星 <250 / 2星 250-400 / 3星 400-525 / 4星 525-600 / 5星 ≥600

3.5.6 组合枚举算法

TechRater 的组合枚举采用回溯法 + 四重剪枝，用于笼子唯一组合、笼和推导等场景。

四重剪枝策略：

  1. 和值剪枝：target ≤ 0 时直接返回
  2. 升序剪枝：v > target 时 break（升序排列，后面更大）
  3. 排除剪枝：已用/已填数字直接跳过
  4. 候选约束剪枝：数字不在任何空格的候选集中时跳过

时间复杂度：最坏 O(C(9, n))，n 为空格数。4格笼最多 126 种组合，实际因四重剪枝远小于理论上限。

三套组合函数层级：

  • _combosHelper() — 基础组合（只考虑和+个数+排除），返回可能出现的数字集合
  • _findAllCombos() — 完整组合枚举（考虑每格候选约束），返回全部组合
  • _canFillSum() — 可行性判断（找到一个可行解就返回），用于快速检测

3.5.7 影响力评分算法

从多个候选结果中选择"最有教学价值"的一步，采用5 维度加权求和。

influence = cageScore × 0.35
          + emptyScore × 0.25
          + candScore × 0.15
          + cageCrossScore × 0.15
          + rule45Score × 0.10

设计理念：以"笼子推进"为核心（Killer数独本质），辅以"区域连锁"和"确定性"，再加两个Killer特有的加分项。权重从高到低符合教学优先级。

选择策略：纯最高分选择，无随机性。Tie-break 规则为先来后到（用 > 而非 >=，保留第一个出现的最高分）。

3.5.8 三阶段剧本提取

从完整解题步骤中提取"开局-破局-收官"三阶段戏剧结构，用于教学演出和关卡评价。

破局点确定：

  • 取深度最高的第一步（技巧深度 = 认知难度）
  • 多个同深度步骤时，取第一个出现的
  • 全是孤星（深度为0）则不生成剧本

级联识别（顺水推舟策略）：破局点之后的所有 fill 步骤都是级联的一部分——"多米诺不需要算，它就是高级技巧破局后引发的雪崩现象。"

级联起点：

  • 破局点为 fill 类型 → 级联从破局点下一个开始
  • 破局点为 elimination 类型 → 级联从之后第一个 fill 开始

  • 冷却时间：默认 3 秒，杀手数独关卡延长至 8 秒
  • 拦截概率：由 AI 性格的 interceptProbability 决定
  • 视觉反馈：红光闪烁 + Boss 气泡台词

3.6.5 必杀技系统

AI 进度达到 70%（第二阶段预警）时触发必杀技，每个 Boss 技能不同：

Boss技能名效果

设局人/残影/秘术圈套瞬间抢占 3 个边缘格子，形成包围态势，连续抢占制造视觉冲击

3.6.6 连击震慑系统

玩家连续填对时触发 AI 震慑（暂停思考），给玩家反击爽感。

  • 触发阈值：标准关卡 3 连击，杀手数独 2 连击（更易触发）
  • 震慑时长：基础 1.5 秒（杀手 2 秒），每多一连击加 0.5 秒（杀手 0.8 秒）
  • 视觉反馈：右侧弹出连击数字（2/3/5/7/10 连，颜色逐级升级），抢格时额外显示"反抢!"
  • 重置条件：填错即重置连击计数

3.6.8 动态难度调节

系统根据玩家填数速度自动调整 AI 速度，实现"遇强则强，遇弱则弱"的自适应体验。

// 核心参数

  speedMultiplier: 1.3,    // 开局慢30%，给玩家适应时间
  targetRatio: 1.3,        // 目标：AI速度 ≈ 玩家的1.3倍（玩家略快）
  minMultiplier: 0.5,      // AI最快 = 基准的50%

3.7 What If 假设模式（分支快照）

What If 模式是一套「假设—验证」的分支推理工具，允许玩家在当前盘面基础上创建快照分支，尝试不同的填数路径，如果发现矛盾可以随时回退，是高级杀手数独解题的利器。

3.7.1 状态机模型

What If 模式的核心是一个快照栈状态机 WhatIfState：

{
  active: false,             // 是否处于 What If 模式
  rootSnapshot: Snapshot,    // 进入模式时的根快照
  snapshots: [ ... ],        // 快照栈（最多3张，第4次覆盖最旧）
  currentIndex: 0,           // 当前所在快照索引
}
卡片式设计 快照在右侧浮条中以扑克牌式堆叠展示：3 张卡片，每张垂直偏移 24px，最新的在最上方。第 4 次创建快照时，最底部（最旧）的快照被自动覆盖。

3.7.2 三种操作

回退（Undo）Backspace回到上一个快照（弹栈），如果已在根快照则退出模式
彻底回退（Revert）Esc放弃所有分支修改，直接回到根快照并退出模式

3.7.3 视觉标识

What-If 模式采用紫罗兰色主题以确保视觉辨识度，与正常模式的默认配色形成明显区分，玩家一眼就能判断当前是否处于假设分支中。

设计原则

紫罗兰色是 What-If 模式的品牌色，贯穿所有视觉元素——数字、边框、卡片、徽章。这种统一的配色策略确保玩家在任何视角下都能快速识别当前的推理状态，避免将假设分支的结果误认为正确答案。

  • 紫色光晕边框：What If 模式激活时，棋盘整体覆盖一层淡紫色光晕边框，明确区分正常模式与假设模式
  • 假设数字样式：假设分支中填入的数字采用紫罗兰色 + 斜体 + 发光效果，与正常数字形成视觉差异
  • 假设模式徽章：棋盘右上角显示"假设中"紫色徽章，带脉冲呼吸动画，持续提醒当前状态
  • 快照缩略图：每张快照卡片自动生成盘面缩略图，紫色渐变边框，方便玩家快速识别不同分支
  • 当前标记：当前所在的快照卡片有高亮边框和"当前"标签
  • 棋盘淡紫色叠层：整个棋盘覆盖一层极淡的紫色叠层，营造"假设空间"的氛围

3.8 连击系统（ComboSystem）

核心 game/combo-system.js

ComboSystem 负责追踪玩家连续正确填数的节奏，通过里程碑奖励和 EUREKA 爆发机制强化心流体验。系统支持双路径 EUREKA 触发（连击型 + 灵感型），并根据盘面尺寸动态调整阈值。

3.8.1 时间窗口机制

连击采用10 秒滑动时间窗口：每次正确填数后重置计时器，若 10 秒内没有下一次正确填数，则连击中断。窗口时间可通过 comboWindowMs 参数配置。

设计考量

10 秒窗口是经过反复调试的平衡点——太短会让玩家感到压力，太长则失去连击的节奏感。对于 4x4 新手盘面，阈值会自动降低以提供更友好的体验。

3.8.2 里程碑档位

标准 9x9 模式下定义了 4 档连击里程碑，每档触发不同的视觉和音效反馈：

连击数里程碑颜色说明
3初鸣琥珀色连击启动，显示连击计数器
5连韵蓝色节奏稳定，计数器变色
8疾风 / EUREKA紫色触发 EUREKA 爆发，全屏闪光 + 粒子效果
10惊雷 / MAX红色最高连击，最强视觉反馈

不同盘面尺寸的里程碑阈值自动适配：

  • 4x4 / 新手模式：2 → 4(EUREKA) → 6(MAX)
  • 6x6：3 → 5 → 6(EUREKA) → 8(MAX)
  • 9x9 标准：3 → 5 → 8(EUREKA) → 10(MAX)

3.8.3 双路径 EUREKA

EUREKA（灵感爆发）有两种触发路径，覆盖不同类型的玩家成就感：

  • 连击型 EUREKA：连续正确填数达到 EUREKA 阈值（9x9 为 8 连击），代表流畅的解题节奏
  • 灵感型 EUREKA：卡顿超过 30 秒后突然填对关键格，代表"想通了"的突破感

两种路径都触发相同的视觉爆发效果（全屏金色闪光 + 粒子迸射 + EUREKA 文字），但内部记录不同的触发类型，便于后续数据分析。

3.8.4 心流阈值与加速效应

连击系统与心流状态深度联动，定义了 4 种心流状态：

状态触发条件视觉效果
cold（冷启动）0 连击无
stale（停滞）连击即将超时计数器微闪
flow（心流）达到一定连击数棋盘边缘蓝色光晕
eureka（爆发）EUREKA 触发全屏金色爆发 + 粒子

进入 flow 状态后，玩家的操作反馈会有微妙的加速效果——动画更流畅、音效更清脆，强化"行云流水"的主观感受。

3.8.5 断连机制

以下情况会导致连击中断：

  • 填错：正常模式下直接归零；新手保护模式下只减 1
  • 擦除：擦除数字视为打断节奏，连击归零
  • 超时：超过 10 秒窗口未正确填数

3.8.6 与对战系统的联动（连击震慑）

在对战模式中，高连击会触发连击震慑效果——当玩家连击达到 5 以上时，AI 对手会出现短暂的"惊讶"反应（思考延迟 + 气泡对话），增加对战的沉浸感和策略深度。

3.9 计时器与暂停系统（GameTimer）

核心 game/game-timer.js

GameTimer 提供精确到秒的游戏计时功能，支持页面隐藏自动暂停、对话暂停嵌套、状态事件通知等特性，是游戏节奏控制的基础设施。

3.9.1 计时精度与格式化

计时器采用 Date.now() 时间戳差值计算，而非简单的 setInterval 计数，确保即使在标签页切换或主线程阻塞后恢复时时间仍然准确。内部累计已运行秒数，每次暂停/继续时通过时间戳对齐保证精度。

时间格式化输出为 MM:SS 格式（补零对齐），通过 getFormattedTime() 方法获取。

// 获取当前时间（秒）
timer.getTime()        // 返回数字，如 125

// 获取格式化字符串
timer.getFormattedTime()  // 返回 "02:05"

3.9.2 页面隐藏自动暂停

默认开启 autoPauseOnHide，通过监听 visibilitychange 事件实现：

  • 用户切换到其他标签页或最小化窗口时，自动暂停计时
  • 用户回到页面时，自动恢复计时
  • 避免了"挂后台导致时间白白流逝"的糟糕体验
实现细节

visibilitychange 事件在 document 上监听，使用 document.hidden 判断可见性。销毁时会自动移除监听器，防止内存泄漏。

3.9.3 对话暂停嵌套机制

剧情对话期间需要暂停计时，但对话可能嵌套出现（如对话中触发子对话）。GameTimer 提供了计数式嵌套暂停：

  • pauseForDialog()：每次调用计数 +1，首次调用时真正暂停
  • resumeFromDialog()：每次调用计数 -1，计数归零时真正恢复
  • 确保无论嵌套多少层对话，都能正确恢复到之前的运行状态
// 对话开始
timer.pauseForDialog();   // 暂停，计数=1

// 子对话开始
timer.pauseForDialog();   // 已暂停，计数=2

// 子对话结束
timer.resumeFromDialog(); // 计数=1，仍暂停

// 对话结束
timer.resumeFromDialog(); // 计数=0，恢复计时

3.9.4 暂停状态事件通知

计时器提供三个回调事件，方便其他系统响应计时状态变化：

回调触发时机参数
onTick每秒触发当前秒数
onPause暂停时触发无
onResume恢复时触发无

3.10 性能分级系统（PerformanceMonitor）

核心 core/PerformanceMonitor.js

性能分级系统通过实时 FPS 检测自动调整渲染画质，确保游戏在不同性能设备上都能流畅运行。系统支持三级画质：High / Medium / Low，可自动降级也可手动切换。

3.10.1 三级画质对比

特性High（高画质）Medium（中画质）Low（低画质）
粒子特效 ✅ 全部开启 ❌ 关闭 ❌ 关闭
光晕/发光效果 ✅ 全部开启 ❌ 关闭 ❌ 关闭

默认策略

默认画质为 High。系统会在游戏运行前进行性能预检（2 秒 FPS 采样），如果平均 FPS 低于 45 则自动降级为 Medium；低于 25 则降级为 Low。玩家也可以在设置面板中手动选择画质等级。

3.10.2 自动降级机制

PerformanceMonitor 采用滑动窗口 + 迟滞阈值策略，避免画质频繁切换：

  • 采样窗口：最近 60 帧的平均 FPS（约 1-2 秒窗口）
  • 降级阈值：连续 3 秒 FPS 低于阈值 → 降一级
  • 升级阈值：连续 10 秒 FPS 高于上限 → 升一级（更保守）
  • 冷却保护：每次画质切换后，5 秒内不再触发切换
  • 最低保障：Low 为最低等级，不再继续降级

3.10.3 核心 API

// 获取当前画质等级

// 手动设置画质
PerformanceMonitor.setLevel('medium')

// 启用/禁用自动降级
PerformanceMonitor.setAutoAdjust(true | false)

// 获取当前 FPS

4. 三幕式节奏引擎（Three-Act Rhythm Engine）

v4.0 核心 专家系统 game/tech-rater-adapter.js

三幕式节奏引擎是 v4.0 的核心升级，围绕"叙事化游戏节奏"理念重构了难度评估、单人通关、对战博弈三大核心系统。通过 TechRaterAdapter 三维相对难度模型，为每一格赋予精准的相对难度标签（绿/黄/红三色），并以此为基础构建分层过关、加权得分、AI 策略等上层玩法。

设计理念

传统数独游戏的节奏是"匀速填格"——玩家从头到尾以相同的节奏推进。三幕式引擎借鉴叙事理论的"起承转合"结构，让每一关都有清晰的新手期→成长期→高潮期→收官期，模拟故事的三幕式节奏曲线，使解题过程更有戏剧张力。

4.1 三幕式参数总览

三幕式节奏引擎通过动态调整游戏核心参数，营造"序章→破局→雪崩"的叙事化节奏曲线。每个阶段对 AI 速度、提示冷却、连击倍率等关键参数施加不同的系数，使玩家在每一关都能体验到清晰的起承转合。

参数第一幕 · 序章第二幕 · 破局第三幕 · 雪崩
AI 速度倍率 × 0.7 × 1.0 × 1.4
提示冷却系数 × 0.8（更快刷新） × 1.0（标准） × 1.5（更慢刷新）
连击倍率 × 1.2（更容易连击） × 1.0（标准） × 1.5（高风险高回报）
进度占比 0% ~ 30% 30% ~ 70% 70% ~ 100%
设计目标 快速正反馈，建立信心 稳步推进，深度思考 高压冲刺，高潮体验

4.1.1 第一幕 · 序章（Prologue）

序章阶段对应关卡的前 30% 进度，设计目标是让玩家快速进入状态，通过密集的正反馈建立信心。

  • AI 减速（×0.7）：给玩家更多思考时间，避免开局即被压制
  • 提示加速（×0.8）：提示冷却更短，遇到困难时能更快获得帮助
  • 连击加成（×1.2）：更容易触发连击，让玩家快速体验心流

4.1.2 第二幕 · 破局（Breakthrough）

破局阶段对应关卡的 30% ~ 70% 进度，是游戏的核心推理段，所有参数回归标准值，考验玩家的真实水平。

  • AI 标准速度（×1.0）：公平博弈，节奏由玩家掌控
  • 提示标准冷却（×1.0）：按正常频率刷新提示
  • 连击标准倍率（×1.0）：按标准规则判定连击

4.1.3 第三幕 · 雪崩（Avalanche）

雪崩阶段对应关卡的后 30% 进度，设计目标是营造高压冲刺的高潮体验，随着格子减少，节奏越来越快。

  • AI 加速（×1.4）：AI 出手更频繁，形成压迫感
  • 提示减速（×1.5）：提示冷却变长，倒逼玩家自主思考
  • 连击爆发（×1.5）：连击倍率更高，收官阶段连续填数带来强烈爽感
参数调节机制

三幕参数由 ThreeActEngine.js 统一管理，通过 AISpeedController 作用于 AI，通过 HintManager 作用于提示冷却，通过 ComboSystem 作用于连击倍率。阶段切换时会触发 actChange 事件，各子系统监听此事件并调整自身参数。

4.2 TechRaterAdapter 三维相对难度模型

TechRaterAdapter 将原有的单一维度难度评分（仅技巧等级）升级为三维相对难度模型，更精准地刻画每一格在求解过程中的实际难度。

维度权重说明
求解顺序
Solve Order		 高 该格在整局求解路径中的先后位置。越早被解出的格子相对难度越低，越靠后难度越高（候选数空间被压缩后可选技巧更受限）。
初始候选数密度
Initial Candidate Density		 中 该格在盘面初始状态下的候选数数量。候选数越多，排除过程越复杂，相对难度越高。
技巧深度
Technique Depth		 高 解出该格所需使用的最高阶数独技巧层级（唯一解 → 区块排除 → 数对 → 三链数 → X-Wing → ...）。技巧越深，难度越高。
设计意义

三维模型解决了旧版"仅用技巧等级判定难度"的两大偏差：(1) 同样技巧等级下，后期格子比前期更难；(2) 候选数多的格子即使技巧简单，实际推理量也更大。新模型为后续三色热力图系统提供了精准的数值基础。

4.1.1 三色系统心理学加权规则

在三维相对难度模型的基础上，三色系统进一步引入心理学加权规则，对分类结果进行动态修正，使最终的绿/黄/红划分更贴近玩家的真实认知体验。

规则触发条件效果心理学依据
1. 空间聚集加权
Spatial Salience		 行/列/宫中任一维度已填数 ≥ 7 该维度内的空格自动升格为 🟢 simple（绿色） 人类视觉系统对"局部高密度区域"有认知优势，当一行只剩 2 个空格时，玩家几乎可以"秒填"。
2. 笼子显著性加权
Cage Salience		 2 格笼，且和值 ≤ 5 或 ≥ 17 笼内两个格子自动升格为 🟢 simple（绿色） 极端和值的 2 格笼组合数极少（如和=3 只有 {1,2}），玩家一眼就能看出答案。
3. 候选数密度兜底
Candidate Density Fallback		 格子候选数 ≤ 2，且原分类为 🔴 gate（红色） 降级为 🟡 core（黄色） 即使技巧等级很高，如果候选数只有 2 个，玩家"蒙也能蒙对"的概率高达 50%。

4.3 单人模式分层过关系统

将传统的"填满即通关"升级为四阶段分层通关，模拟叙事游戏的"三幕式"节奏曲线，让玩家在每一关都能体验到清晰的起承转合。

阶段通关条件设计目标占比（参考）
新手阶段（Opening） 填出前 15% 的格子 快速正反馈，让玩家迅速进入状态 ~15%
中盘阶段（Development） 填出 50% 的格子 主推理阶段，考验技巧掌握 ~35%

4.2.1 雪崩自动补全机制

当剩余格子数低于阈值且全部为"唯一候选数"级别时，系统触发雪崩自动补全（Avalanche Auto-Fill），将收尾阶段的机械劳动转化为一次性的视觉爆发效果，避免玩家在"最后 5 格"产生拖沓感。

触发条件

雪崩机制仅在剩余所有格子均可通过"裸单"（Naked Single）直接填出时触发，确保不会跳过任何有推理价值的步骤。触发前会有明显的视觉提示（最后一格高亮脉冲）。

4.4 对战模式加权得分系统

对战模式从"比谁填得多"升级为三色加权得分制，鼓励玩家主动攻克高难度格子，而不是抢填简单格。

颜色难度等级得分权重策略价值
🟢 绿色简单（新手级）× 1.0快速积累基础分，适合开局抢节奏
🟡 黄色中等（中盘级）× 1.5性价比最高，是得分主力
🔴 红色困难（Boss 级）× 2.0高分差来源，翻盘关键

4.3.1 胜利判定：75% 阈值规则

对战不再以"填满盘面"为终点，而是以加权得分达到总分的 75%为胜利条件。这一设计确保：

  • 不会打满全场：实力有差距时，约在 70%~80% 进度即可分出胜负
  • 红色格战略价值高：抢到关键红色格可能直接拉开分差触发胜利
  • 避免垃圾时间：胜负已分后无需机械填完剩余简单格

加权进度公式：

加权进度 = (绿格数×1 + 黄格数×1.5 + 红格数×2) / 最大加权分

核心设计原则

GameContext 是五层系统的唯一可信数据源。各层之间不直接调用对方的内部方法，而是通过读写 GameContext 中的状态进行通信。这种设计确保了各层的低耦合——替换感知层的实现不影响决策层，升级学习层不需要修改表达层。

5.2.2 五层联动工作流

以"玩家卡顿后获得提示"为例，五层联动的完整工作流如下：

  1. 感知层检测：PlayerStateMonitor 发现玩家 30 秒未填数，stuck 指标升高 → 写入 player.stuck = true
  2. 决策层响应：DecisionEngine 读取到 stuck 状态，结合 learning 中的技巧掌握度，判定应触发"卡顿引导" → 写入 decision.action = SHOW_TOAST
  3. 节拍层对齐：BeatQuantizer 检查当前是否处于反馈冷却期，若不在冷却则放行行动
  4. 表达层执行：ExpressionDirector 从 decision 队列取出行动，调度角色气泡组件显示引导提示
  5. 学习层反馈：LearningSystem 记录玩家看到提示后的行为变化（是否采纳、是否继续卡顿），更新 learning.mastery 和 learning.thresholds
  6. 决策层迭代：下次决策时，DecisionEngine 会参考更新后的学习状态，调整提示的时机和内容深度

GameContext 支持状态变更事件，各层可以订阅感兴趣的状态变化：

5.5 回放系统（ReplaySystem）

专家系统 expert/replay-system.js

ReplaySystem 构建于 Board.history 之上，提供完整的对局录制与回放功能。支持逐步骤回放、关键帧标记、倍速播放等特性，是教学演示、错题回顾和分享功能的基础组件。

5.4.1 录制数据结构

回放系统在 Board 历史记录的基础上，构建了标准化的步骤数据结构：

字段类型说明
indexnumber步骤序号
typestring步骤类型（填数/擦除/候选切换/批量操作等）
cellsArray涉及的格子坐标列表

支持的步骤类型（STEP_TYPES）：

  • fillNumber / eraseNumber：填数 / 擦除
  • toggleCandidate / batchToggleCandidate：候选数切换 / 批量切换
  • toggleElimination / batchToggleElimination：排除标记切换
  • batchErase：批量擦除
  • clearAllCandidates：清空所有候选
  • autoFillCandidates：自动填充候选
  • setNumberAt：直接设置数字

5.4.2 关键帧检测

系统会自动检测并标记关键步骤（Key Steps），用于快速定位重要时刻：

关键帧类型触发条件

correction（纠错）擦除了之前填入的错误数字并重新填对
majorElimination（重大排除）一次性排除大量候选数（默认 ≥ 10 个）

基线快照机制

录制开始时会保存棋盘的基线快照（baseline snapshot），回放时从基线状态逐步应用步骤，确保回放的准确性。回放结束后自动恢复原始棋盘状态，不影响当前游戏进度。

5.4.4 事件回调

  • onPlayEnd：回放结束时触发

9.1.3 三份备份机制

为防止数据丢失，关键数据（进度/成就/学习记录）采用三份备份轮转策略：

  • 主存档：当前正在使用的存档数据
  • 备份 A：上一次成功保存的快照
  • 备份 B：上上次成功保存的快照

每次保存时：主存档 → 备份 A → 备份 B（轮转）。如果主存档损坏，自动从备份 A 恢复；备份 A 也损坏则从备份 B 恢复。

9.2 错误日志持久化

全局错误捕获系统将运行时错误持久化到本地存储，便于调试和问题排查。

9.2.1 双重错误捕获

系统通过两个层面捕获错误：

  • window.onerror：捕获同步代码错误和资源加载失败
  • window.onunhandledrejection：捕获 Promise 未处理的拒绝（异步错误）

9.2.2 50 条 FIFO 队列

错误日志采用先进先出（FIFO）队列，最多保留 50 条记录，超过时自动丢弃最旧的条目：

{
  timestamp: 1690000000000,  // 时间戳
  type: 'error' | 'unhandledrejection',
  message: '错误信息',
  stack: '调用栈信息',
  url: '当前页面URL',
  userAgent: '浏览器UA',
  levelState: '当前关卡ID'
}

9.2.3 防抖写入

为避免频繁写入 localStorage 影响性能，错误日志采用防抖写入策略：

  • 错误发生时先存入内存队列
  • 防抖延迟 2 秒后批量写入 localStorage
  • 页面卸载前（beforeunload）强制 flush 一次

9.3 存档校验与备份轮转

9.3.1 存档校验和

每份存档数据都附带一个校验和（checksum），用于检测数据损坏：

{
  data: { ... },           // 实际数据
  checksum: 'sha256_hash', // 数据哈希值
  version: 4,             // Schema 版本
  savedAt: 1690000000000 // 保存时间
}

加载存档时，重新计算数据的哈希值并与存储的校验和对比，如果不一致则判定为损坏，自动回退到备份。

9.3.2 备份轮转策略

备份轮转的触发时机：

  • 自动备份：每次成功保存主存档时，自动轮转备份
  • 定时备份：游戏每 5 分钟自动保存一次（仅在有变化时）
  • 关键节点备份：关卡通关、成就解锁等关键时刻强制备份
数据安全

所有备份均存储在浏览器 localStorage 中，清除浏览器数据会导致存档丢失。建议玩家定期导出存档（设置 → 数据管理 → 导出存档）作为额外备份。

9.4 内容安全策略（CSP）

游戏遵循严格的内容安全策略（Content Security Policy），降低 XSS 等安全风险。

9.4.1 CSP 指令

指令策略说明
default-src 'self' 默认只允许加载同源资源
script-src 'self' 只允许执行同源脚本
style-src 'self' 'unsafe-inline' 允许内联样式（用于动态样式）
img-src 'self' data: 允许同源图片和 data URI
media-src 'self' data: 允许同源音视频和 data URI
connect-src 'self' 只允许同源网络请求
frame-src 'none' 禁止 iframe 嵌入
object-src 'none' 禁止插件

9.4.2 实施方式

CSP 通过 HTTP 或 meta 标签两种方式部署：

<meta http-equiv="Content-Security-Policy"
      content="default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; ...">
为什么 'unsafe-inline' 用于样式？

游戏中大量使用动态内联样式（如 Canvas 渲染动画、动态颜色计算等），无法避免内联样式的安全风险远低于内联脚本，因此保留 style-src 允许 'unsafe-inline'。

11.5 关卡设计规范

定向技巧关卡的设计方法论，确保关卡既能有效教学，又有足够的挑战性和沉浸感。

10.5.1 七步设计法

  1. 确定教学目标 — 明确目标技巧、难度等级、盘面尺寸，撰写 teachingGoal
  2. 构造解盘 + 设计锚点 — 准备完整正解，设计 2-3 个锚点（SINGLE 或 PAIR_CONSTRAINED）确保关键模式不被破坏
  3. 笼子定向生长 — 纵向生长（垂直权重1.5），跨宫笼比例 ≥25%
  4. 唯一解验证 — MRV-BFS 求解器验证，多解则调整锚点
  5. 减法校验必要性 — 禁用目标技巧后是否卡住，目标状态为 PERFECT
  6. 纯净度验证 — 技术断点 + 唯一破局技巧 + 级联坍塌≥4格
  7. 质量收尾 — coreMove、keyCells、features、triggers、统计数据

10.5.2 锚点设计原则

锚点是关卡中预先固定的笼子，在生成过程中不参与随机生长。

锚点类型格式用途
SINGLE单格笼，直接锁定一个已知数强制某个关键位置的数值
PAIR_CONSTRAINED双格约束笼，锁定一个两格组合强制形成特定组合约束（如 NakedPair 的候选模式）

设计原则：

  • 锚点数量：通常 2-3 个，不宜过多（否则限制生长空间）
  • 位置策略：分散在盘面不同区域，避免局部过密
  • 锚点是关卡的"骨架"，确保目标技巧的核心模式稳定出现

10.5.3 技巧必要性验证（减法校验）

核心思路：切除目标技巧后看是否还能解——如果切掉就解不动，说明该技巧是必须的。

评估结果含义分数
UNSOLVABLE关卡本身无解0
TOO_EASY最高技巧低于目标等级10
BYPASSED禁用目标技巧后仍能通关（技巧不必要）30
PERFECT必须使用目标技巧才能推进100+

10.5.4 纯净度三重标准

flowchart LR A[技术断点] --> B[技巧纯净] B --> C[级联坍塌≥4格] A:::crit -->|基础技巧完全解不动| A B:::crit -->|唯一能推进的就是目标技巧| B C:::crit -->|破局后多米诺效应| C classDef crit fill:#2a2f3a,stroke:#6366f1
  1. 技术断点：先用低于目标等级的所有技巧解题，直到完全卡住
  2. 技巧纯净：从断点开始推进，最高级 elimination 必须就是目标技巧
  3. 级联坍塌：核心破局格填入后，引发 ≥4 格连锁填充（多米诺骨牌效应）

12. 关卡验证系统（LevelValidator）

工具链 核心

LevelValidator 是 Phase E 新增的关卡质量保障工具，负责对每一道关卡进行自动化、标准化的三重验证。它既是开发阶段的 CI 检查器，也是关卡设计时的实时反馈工具。

12.1 设计目标

在 cagemaster2 时代，关卡验证完全依赖人工——设计完一道关后，需要手动跑求解器、核对笼子和值、确认唯一解。这个过程既繁琐又容易遗漏。LevelValidator 的诞生就是为了把这些重复劳动自动化：

  • 数据完整性：确保关卡数据格式正确、笼子不重叠不遗漏、和值一致
  • 可解性验证：确认关卡有且仅有一个解
  • 难度评级：给出客观的星级和分数，与设计目标对比
  • 批量自动化：一次验证整个题库，生成汇总报告
设计哲学

LevelValidator 不负责「创造好关卡」，它负责「拦住坏关卡」。把住质量底线，让设计师把精力放在创意上。

12.2 三重验证体系

flowchart TD A[关卡数据] --> B[第一重：数据完整性] B -->|通过| C[第二重：可解性验证] B -->|失败| X[数据错误报告] C -->|通过| D[第三重：难度评级] C -->|失败| Y[可解性错误报告] D --> Z[验证报告] classDef crit fill:#2a2f3a,stroke:#6366f1 class A,B,C,D crit

三重验证逐层递进，前一重不通过则不进入下一重，避免无效计算。

12.3 数据完整性检查

第一重验证是纯静态检查，不涉及求解逻辑，速度极快（微秒级）。

11.3.2 笼子连通性算法

采用 BFS 广度优先搜索验证连通性：

function _isCageConnected(cells, gridSize) {
  if (cells.length <= 1) return true;
  const visited = new Set();
  const queue = [cells[0]];
  visited.add(cells[0].row * gridSize + cells[0].col);

  while (queue.length > 0) {
    const curr = queue.shift();
    for (const [dr, dc] of [[-1,0],[1,0],[0,-1],[0,1]]) {
      const nr = curr.row + dr, nc = curr.col + dc;
      const key = nr * gridSize + nc;
      if (!visited.has(key) && cells.some(c => c.row === nr && c.col === nc)) {
        visited.add(key);
        queue.push({ row: nr, col: nc });
      }
    }
  }
  return visited.size === cells.length;
}

12.4 可解性验证

第二重验证确认关卡有且仅有一个解，采用双层策略：

  1. 逻辑求解层（TechRater）：用人类技巧逐步推导，能解出说明关卡符合人类解题逻辑
  2. 暴力回溯层（BacktrackSolver）：MRV 启发式回溯，统计解的数量，确保唯一解
为什么需要两层？

TechRater 只能解出「人类能解的关」，如果它解不出来，不代表关卡无解——可能只是需要更高级的技巧。暴力回溯不依赖技巧，能穷举所有解，但速度慢。两者配合，既确认可解性，又评估人类可达性。

10.4.1 验证流程

1. 用 TechRater 完整求解
   → 成功：记录求解路径和最高技巧
   → 失败：标记为「超出技巧范围」，进入暴力验证

2. 用 BacktrackSolver 暴力求解（最多找2个解）
   → 0 个解：无解（error）
   → 1 个解：唯一解（通过）
   → ≥2 个解：多解（error）

3. 对比两层结果
   → TechRater 解出 && 暴力唯一解 → 优质关卡
   → TechRater 未解出 && 暴力唯一解 → 高难度 / 需高级技巧
   → 暴力多解 → 不合格

12.5 批量验证工具

LevelValidator 提供命令行批量验证能力，支持对整个题库进行一次性扫描。

13. 技巧纯净度验证（TechnicalPurityValidator）

工具链 专家

技巧纯净度验证是定向技巧关卡的质检核心。一道「高纯度定向技巧关」不仅仅是「需要用到某个技巧」，而是要求该技巧以最纯粹、最有教学价值的方式出现。

13.1 什么是「高纯度定向技巧关」

想象一下，你想教玩家 X-Wing 技巧。如果一道关需要先用 3 个其他高级技巧做铺垫，才能到达 X-Wing 的破局点，那这道关的教学效果就大打折扣——玩家还没等到 X-Wing，已经被前面的技巧劝退了。

高纯度定向技巧关的定义：

纯净度定义

用低于目标等级的技巧解题，解到完全卡住（技术断点）；此时唯一能推进的就是目标技巧（技巧纯净）；用出目标技巧后，触发连续的连锁填充（级联坍塌）。

13.2 三重纯净标准详解

11.2.1 第一重：技术断点（Technical Breakpoint）

定义：使用低于目标技巧等级的所有技巧持续求解，直到盘面不再变化。

验证方法——受限求解模式：

function solveWithTechCap(level, targetLevel) {
  const solver = TechRater.fromLevel(level);
  solver.setEnabledTechniques(
    ALL_TECHNIQUES.filter(t => t.level < targetLevel)
  );
  const result = solver.solve(500); // 最多500步
  return {
    breakpointBoard: result.finalBoard,
    remainingCells: result.remaining,
    reachedLimit: result.stalled  // 是否卡住
  };
}

断点的合格标准：

  • 必须进入 stalled 状态（低级技巧确实解不动了）
  • 剩余空格数 ≥ 5（不能还没怎么解就到断点了）
  • 断点不能是开局（剩余 = 总空格数）

11.2.2 第二重：技巧纯净（Technique Purity）

定义：从技术断点继续推进，第一个有实质进展的 elimination 步骤就是目标技巧。

什么叫「实质进展」？就是能排除候选数、直接导向填数的那一步。具体标准：

  • 该步骤的技巧等级 = 目标技巧等级
  • 该步骤能排除 ≥ 1 个候选数
  • 排除候选后，接下来的 fill 步骤能直接推进
  • 断点和破局点之间，没有其他同级或更高级技巧
为什么强调「第一个」？

如果玩家在断点处面对多个可选的高级技巧路径，说明关卡不够「定向」——玩家可能通过另一个技巧绕过，那就达不到教学目标技巧的目的。

11.2.3 第三重：级联坍塌（Cascade Collapse）

定义：破局格填入后，连续触发 ≥ 4 格的连锁填充（多米诺骨牌效应）。

级联坍塌是衡量「爽感」的指标。破局技巧用出来之后，如果只是填了一个格就又卡住了，玩家的成就感会很弱。但如果触发了一连串的连锁反应，那种「打通任督二脉」的感觉会非常强烈。

级联计数规则：

  • 从破局点之后的第一个 fill 开始计数
  • 只计数裸单（nakedSingle）级别的连锁
  • 遇到需要更高级技巧才能推进时，级联结束
  • 级联长度 = 连续裸单填充的格数

13.4 受限求解模式的实现原理

受限求解是纯净度验证的核心技术。它的基本思想是：选择性地禁用某些技巧，然后看求解器能走多远。

11.4.1 实现要点

class RestrictedTechRater extends TechRater {
  constructor(board, options = {}) {
    super(board);
    this.disabledTechniques = new Set(options.disabled || []);
    this.maxTechLevel = options.maxTechLevel || 10;
  }

  _tryTechnique(techId) {
    // 禁用列表中的技巧直接跳过
    if (this.disabledTechniques.has(techId)) return null;
    // 超过等级上限的技巧跳过
    const tech = TECHNIQUE_MAP[techId];
    if (tech.level > this.maxTechLevel) return null;
    return super._tryTechnique(techId);
  }
}

11.4.2 断点稳定性检查

为了防止「假断点」（求解器因为遍历顺序问题提前卡住），需要做稳定性检查：

// 多轮验证确保断点稳定
function verifyBreakpointStability(level, targetLevel, rounds = 3) {
  const breakpoints = [];
  for (let i = 0; i < rounds; i++) {
    // 每轮打乱技巧遍历顺序（同一等级内）
    const result = solveWithTechCap(level, targetLevel, { shuffle: true });
    breakpoints.push(result.remainingCells);
  }
  // 所有轮次剩余格数一致 → 断点稳定
  return breakpoints.every(n => n === breakpoints[0]);
}

13.5 顺水推舟策略

「顺水推舟」是纯净度优化中的一个重要策略：当断点不是很纯净（有多个同级技巧可选）时，不是推翻重来，而是通过微调笼子布局，让目标技巧成为「最先被看到」的那个。

具体做法：

  1. 分析断点处所有可用的同级技巧
  2. 找出目标技巧的关键格和证据链
  3. 调整相邻笼子的和值或形状，让目标技巧的排除效果更显著
  4. 或者反过来，让其他可选技巧的排除效果变弱
设计经验

与其从零设计一道纯净关，不如先设计一道「大致对路」的关，再用纯净度验证工具反复迭代优化。通常经过 3-5 轮调整就能从 B 级提升到 A 级。

14. 关卡生成器（cage-fixer-v7）

工具链 数据

cage-fixer-v6 是 cagemaster3 的自动化关卡生成器，也是 Phase E 工具链的核心产出。它可以从零生成符合规范的杀手数独关卡，支持难度控制、技巧定向和纯净度校验。

14.1 命名由来与设计哲学

为什么叫「cage-fixer」？因为前五代生成器的核心问题都是「笼子划分不合理」——要么形状奇怪，要么和值冲突，要么唯一解不成立。v6 的目标就是把笼子划分这个难题彻底解决。

设计哲学：

  • 从解出发：先生成完整正解，再划分笼子，保证和值天然正确
  • 生长算法：笼子从种子格开始生长，保证连通性和自然形状
  • 唯一解优先：每一步挖洞都验证唯一解，不做无效尝试
  • 难度可调控：通过笼子大小分布、挖洞策略逼近目标星级

14.2 七步生成流水线

12.2.1 Step 1：生成完整解

用随机回溯法生成一个合法的数独终盘。这一步是整个流水线的基础。

算法：回溯 + MRV（最少剩余值）启发式

  • 按空格候选数从小到大填充（MRV），加速收敛
  • 每格随机选择候选数字，确保多样性
  • 9×9 终盘生成平均耗时 < 5ms
function generateSolution(gridSize = 9) {
  const board = Array(gridSize).fill(null).map(() => Array(gridSize).fill(0));
  return backtrack(board, gridSize);
}

function backtrack(board, n) {
  // 找候选最少的空格（MRV）
  const [row, col, candidates] = findMRVCell(board, n);
  if (row === -1) return board; // 全部填满

  // 随机打乱候选顺序
  shuffle(candidates);

  for (const num of candidates) {
    if (isValidPlacement(board, row, col, num, n)) {
      board[row][col] = num;
      const result = backtrack(board, n);
      if (result) return result;
      board[row][col] = 0;
    }
  }
  return null;
}

12.2.2 Step 2：划分笼子

采用生长算法划分笼子，同时满足「数字不重复」约束（同一笼内数字各不相同）。

算法流程：

  1. 随机选择一个未分配的格子作为种子
  2. 从种子开始向四邻生长，每次选择一个邻居加入笼子
  3. 生长约束：新格子的数字在笼子中不重复（杀手数独规则）
  4. 停止条件：达到目标笼子大小，或没有可生长的邻居
  5. 重复直到所有格子被分配

笼子大小分布是控制难度的关键参数之一：

12.2.3 Step 3：计算和值

最直接的一步——对每个笼子，把其中的答案数字相加，就是笼子的和值。

function calculateCageSums(solution, cages) {
  return cages.map(cage => {
    const sum = cage.cells.reduce((s, [r, c]) => s + solution[r][c], 0);
    return { ...cage, sum };
  });
}

因为是从正解出发，所以和值天然正确，不会有冲突。

12.2.4 Step 4：挖洞

挖洞是生成有唯一解的谜题的核心步骤。策略是随机挖洞 + 唯一解验证。

算法流程：

  1. 从全满盘面开始
  2. 随机选择一个格子，尝试移除其数字（变成空格）
  3. 用求解器验证是否仍为唯一解
  4. 唯一解 → 保留挖洞；不唯一 → 恢复数字
  5. 重复直到挖不动为止，或达到目标空格数
唯一解验证的双层策略

挖洞阶段的唯一解验证是性能瓶颈。v6 采用双层策略：先用 TechRater 快速验证（逻辑求解），如果 TechRater 解出唯一解就直接通过；如果 TechRater 解不出来（可能多解也可能只是技巧不够），再用暴力回溯验证。这样 90% 以上的情况不需要暴力回溯，大幅提升速度。

12.2.5 Step 5：难度调节

挖洞完成后，用 TechRater 评估难度。如果与目标星级差距较大，则进行调整：

  • 太难了：回填几个关键位置的数字（降低空格数）
  • 太简单了：继续挖洞（增加空格数），或者调整笼子
  • 技巧等级不够：调整笼子大小分布，增加大笼比例

难度逼近采用二分策略：先大幅度调整，接近目标后逐步细化，通常 3-5 轮迭代即可收敛到目标星级。

12.2.6 Step 6：纯净度校验（可选）

如果指定了目标技巧（如生成定向教学关），则在最后一步调用 TechnicalPurityValidator 进行纯净度校验。

纯净度不达标时的处理策略：

  • 分数接近（B级以上） → 微调笼子后重试
  • 分数差距大 → 丢弃本次生成，重新开始
  • 纯净关生成成功率较低（约 5-15%），需要多轮尝试

14.3.2 解锁判定逻辑

class SealManager {
  // 关卡完成时检查是否解锁印记
  checkSealUnlock(levelId, runStats) {
    const seal = SEAL_DEFS.find(s => s.levelId === levelId);
    if (!seal || this.isUnlocked(seal.id)) return null;

    const conditions = seal.conditions;
    const passed = this._checkConditions(conditions, runStats);

    if (passed) {
      this._unlockSeal(seal.id);
      return seal;
    }
    return null;
  }

  _checkConditions(conditions, stats) {
    if (conditions.noHints && stats.hintsUsed > 0) return false;
    if (conditions.noErrors && stats.errors > 0) return false;
    if (conditions.timeLimit && stats.time > conditions.timeLimit) return false;
    if (conditions.noUndo && stats.undoCount > 0) return false;
    if (conditions.minCombo && stats.maxCombo < conditions.minCombo) return false;
    if (conditions.requiresSeals) {
      for (const reqId of conditions.requiresSeals) {
        if (!this.isUnlocked(reqId)) return false;
      }
    }
    return true;
  }
}

17. TechRater Bug 修复记录（v2.3 → v2.4）

技术附录 核心

Phase E 对 TechRater 推理引擎进行了一次系统性的 Bug 修复，版本号从 v2.3 升级到 v2.4。本次修复涉及 4 个关键问题，其中部分问题会影响难度评级的准确性和提示系统的正确性。

17.1 Bug #1：X-Wing/Swordfish 高亮轴硬编码

15.1.1 现象

X-Wing 和 Swordfish 技巧在返回高亮信息时，行/列轴的方向是硬编码的——X-Wing 永远返回「行为基」的高亮，Swordfish 也是如此。但实际上 X-Wing 既可以是行基（两行中的候选构成矩形），也可以是列基（两列中的候选构成矩形）。硬编码导致列基的 X-Wing 高亮显示错误——本该高亮两列，结果高亮了两行。

15.1.2 原因

原始实现中，_findXWing() 函数只扫描了行方向的模式，找到匹配后直接将行作为主轴返回。没有区分「行基 X-Wing」和「列基 X-Wing」，高亮轴的计算写死为行。

// v2.3 中的问题代码（简化）
_findXWing() {
  // 只扫描行方向
  for (let row1 = 0; row1 < 9; row1++) {
    for (let row2 = row1 + 1; row2 < 9; row2++) {
      // ... 找两行间的 X-Wing 模式
      if (found) {
        return {
          type: 'xWing',
          highlightRows: [row1, row2],  // 硬编码：只有行
          highlightCols: [],            // 列永远为空！
          // ...
        };
      }
    }
  }
}

15.1.3 修复方案

增加列方向的扫描，并根据实际检测到的模式正确设置高亮轴：

// v2.4 修复后
_findXWing() {
  // 行基 X-Wing（两行中，某数字只出现在相同两列）
  const rowBased = this._findXWingRows();
  if (rowBased) {
    return {
      ...rowBased,
      highlightRows: rowBased.bases,     // 两行
      highlightCols: rowBased.peers,     // 两列（排除的位置）
      orientation: 'row'
    };
  }

  // 列基 X-Wing（两列中，某数字只出现在相同两行）
  const colBased = this._findXWingCols();
  if (colBased) {
    return {
      ...colBased,
      highlightRows: colBased.peers,     // 两行（排除的位置）
      highlightCols: colBased.bases,     // 两列
      orientation: 'col'
    };
  }

  return null;
}

15.1.4 影响范围

  • 提示系统：列基 X-Wing 的提示高亮错误，玩家看到的高亮位置不对 → 高影响
  • 技巧图鉴：示例高亮显示错误 → 中影响
  • 难度评级：不影响（是否检测到与高亮无关） → 无影响

17.2 Bug #2：X-Wing/Swordfish 只返回第一个结果

15.2.1 现象

X-Wing 和 Swordfish 的检测函数找到第一个匹配后就立即返回，没有继续寻找其他可能的模式。这导致两个问题：

  1. 当盘面上有多个 X-Wing 时，只返回最先找到的那个
  2. 影响力评分失效——因为只有一个候选，无法比较「哪个更有教学价值」

15.2.2 原因

早期实现中，X-Wing 等高级技巧被认为是稀有的，一盘最多一个，所以找到就返回。但随着题库扩大，尤其是高难度关卡中，可能同时存在多个 X-Wing 模式。

// v2.3 中的问题
_findXWing() {
  for (...) {
    if (found) {
      return result;  // 找到就返回，不继续找
    }
  }
  return null;
}

15.2.3 修复方案

收集所有候选结果，然后通过影响力评分选出最优解：

// v2.4 修复后
_findXWing() {
  const candidates = [];

  // 收集所有行基 X-Wing
  for (...) {
    if (found) candidates.push(result);
  }

  // 收集所有列基 X-Wing
  for (...) {
    if (found) candidates.push(result);
  }

  if (candidates.length === 0) return null;

  // 按影响力评分排序，返回最优解
  candidates.sort((a, b) => this._calcInfluence(b) - this._calcInfluence(a));
  return candidates[0];
}

15.2.4 影响范围

  • 提示系统：可能会选择不同的 X-Wing 作为提示目标（更有教学价值的那个） → 中影响
  • 影响力评分：高级技巧的影响力评分现在有效了 → 高影响（对教学质量）
  • 求解路径：可能改变求解顺序，因为选择了不同的 X-Wing → 低影响
  • 难度评级：基本不影响，最高技巧等级不变 → 无影响

17.3 Bug #3：Rule45 只返回第一个结果

15.3.1 现象

与 Bug #2 类似，Rule45（45法则/星衡法则）的检测函数也是找到第一个可计算的伸出/伸入格就返回。当一宫内有多个可用的 45 法则推导时，只返回最先找到的那个，跳过了可能更有教学价值的选项。

15.3.2 原因

Rule45 的实现沿用了早期「找到即返回」的模式。在简单关卡中问题不大，但在笼子布局复杂的关卡中，可能同时存在 3-5 个可用的 Rule45 推导，优先级选择很重要。

15.3.3 修复方案

与 X-Wing 的修复思路一致——收集全部候选，按影响力排序：

// v2.4 修复后
_findRule45() {
  const candidates = [];

  // 扫描所有宫的伸出格（outie）
  for (let box = 0; box < 9; box++) {
    const outies = this._findOutieCells(box);
    for (const outie of outies) {
      candidates.push({
        type: 'rule45',
        subtype: 'outie',
        box,
        cell: outie.cell,
        value: outie.value,
        cageSum: outie.cageSum,
        boxSum: outie.boxSum,
        evidence: outie.evidence
      });
    }
  }

  // 扫描所有宫的伸入格（innie）
  // ... 同上

  if (candidates.length === 0) return null;

  // 优先级：直接出数 > 单格伸入/伸出 > 多格
  candidates.sort((a, b) => {
    const priority = { fill: 3, single: 2, multi: 1 };
    return priority[b.subtype] - priority[a.subtype];
  });

  return candidates[0];
}

15.3.4 影响范围

  • 提示系统：优先选择最直观的 Rule45 推导（直接出数的），教学效果更好 → 中高影响
  • 求解路径：可能加快求解速度，因为优先选直接出数的 → 低影响
  • 难度评级：基本不影响 → 无影响

17.4 Bug #4：_fillCell 后不重新应用笼约束

15.4.1 现象

这是最严重的一个 Bug。当 TechRater 通过某种技巧填入一个数字后（_fillCell），没有重新计算受影响笼子的组合约束，导致后续的候选排除不完整。

具体表现：某些关卡中，TechRater 会「卡住」，认为需要更高级的技巧，但实际上用笼子唯一组合就可以继续推进——只是因为填数后没有刷新笼子的候选组合，所以没检测到。

15.4.2 原因

_fillCell 方法只更新了格子的值和同行列宫的候选排除，但没有触发「笼子组合重算」。笼子的唯一组合检测是基于初始候选集做的，当某个笼子里填入新数字后，剩余空格的可能组合会收缩，甚至可能出现新的唯一组合——但这些都没有被重新计算。

// v2.3 中的问题
_fillCell(row, col, num, technique) {
  this.board[row][col] = num;
  this._eliminateFromRow(row, num);     // 排除行
  this._eliminateFromCol(col, num);     // 排除列
  this._eliminateFromBox(row, col, num); // 排除宫
  // ⚠️ 漏掉了：重新计算该格子所在笼子的组合约束！
}

15.4.3 修复方案

在 _fillCell 中增加笼子约束的重新应用：

// v2.4 修复后
_fillCell(row, col, num, technique) {
  this.board[row][col] = num;
  this._eliminateFromRow(row, num);
  this._eliminateFromCol(col, num);
  this._eliminateFromBox(row, col, num);

  // 重新应用所在笼子的组合约束
  const cage = this._getCageAt(row, col);
  if (cage) {
    const newEliminations = this._recalcCageCombinations(cage);
    // 如果新排除了候选，可能触发连锁，需要传播
    if (newEliminations.length > 0) {
      this._propagateEliminations(newEliminations);
    }
  }

  // 记录步骤
  this.steps.push({ type: 'fill', row, col, num, technique });
}

15.4.4 影响范围

高影响 Bug

这是 v2.3 中最严重的 Bug，直接影响求解能力和难度评级的准确性。修复后，部分之前被评为 4-5 星的关卡实际只需要 3 星技巧就能解出。

  • 求解能力：TechRater 能解出更多关卡（约 8% 的关卡评级下降） → 高影响
  • 难度评级：部分关卡的星级评定偏高，修复后需要重新评级 → 高影响
  • 提示系统：某些关卡中提示系统会说「需要更高级技巧」，但实际上用笼子组合就能推进 → 中高影响
  • 纯净度验证：断点位置可能变化，影响纯净度评分 → 中影响
